# SRUI Architecture

# 1. Overview

SRUI is a screen-reader-first UI toolkit for .NET. It maintains a retained semantic tree of widgets, processes keyboard input against that tree, and emits structured accessibility events describing what the user should perceive. It produces no pixels and never will: visual rendering is permanently out of scope. What an application does with the events — synthesize speech, drive a braille display, back a platform accessibility API — is decided by the readers attached to it (section 7).

The toolkit is pure C# from the application surface down to the engine. Native code appears only at the platform edges — SDL3 for the window and keyboard, Prism for speech, cosmos/phonon for game audio — each reached through hand-written P/Invoke (section 11).

# 2. Design Principles

## 2.1. Sans-IO engine

The engine owns no platform resources: no TTS engine, no clipboard, no window, no event loop, no file access, no wall clock (time is injected). The host pushes input in and drains events out. Platform services the engine needs (clipboard) are injected behind interfaces. This keeps the engine headless and deterministic under test — a headless `SruiApp` is a complete, drivable application with no native dependencies.

## 2.2. One object per widget, described by its fields

A widget is a single object: the application-facing surface, the widget's state, and its input behavior live together in a `Widget` subclass, and that object is its node in the semantic tree. Identity on the public surface is the object reference — there are no handles to go stale, and events reach their widget directly. What the user can know about a widget is its fields (section 4.2): typed properties the widget declares, read by the engine at the end of every tick. Nothing is synchronized and nothing is announced by the widget: program code changes fields, or binds them to its own model so they change by themselves, and the framework speaks the difference between what the user last heard and what is now under the cursor (section 7.2).

## 2.3. Structured events out; readers render

The engine never speaks. It emits structured accessibility events carrying typed payloads (`AccessibilityEvent`: field values with their keys, focus arrivals, action events). Speech composition is provided as a library (`SpeechRenderer`: a tick's events in, utterances out) that readers may use or bypass, and whose per-field rendering tables programs extend for fields of their own. This is what lets one event stream feed a self-voicing reader, a braille reader, a UIA provider, and a test harness simultaneously — and what keeps every spoken word out of the engine and the widgets, where a translation or a sound-based reader could never reach it.

## 2.4. Policy-free

Application vocabulary stays out of the engine: no application command names, no command categories, no persistence formats, no application-global shortcuts. The engine supplies mechanisms (key combos, binding maps, conflict detection) and the host supplies policy. Serialization of user configuration is host-owned; the engine exposes stable string forms (for example `"ctrl+shift+s"` for key combos) and plain data structures.

# 4. The Semantic Tree

## 4.1. Nodes and widgets

The tree owns all nodes in a dictionary keyed by an engine-internal handle allocated from a monotonic counter and never reused; resolution is O(1) and a stale handle resolves to nothing rather than to a recycled node. Each node stores its parent, an ordered child list, its structural traits (focusable, context label, hidden, disabled, shortcuts — the things navigation and dispatch consult), and a reference to the `Widget` object that embodies it — the object that handles the node's input, receives its events, and carries everything spoken. Handles never cross the public surface: applications hold widget objects, and an event queued for a widget that has since been removed resolves to nothing and is dropped at dispatch.

## 4.2. Fields

Everything a reader can know about a widget, or about an item a list or tree holds, is a field: a typed key (`Field<T>`, compared by reference) and a value. The core keys live in `Fields` — name, role, description, shortcuts, the flag states (disabled, required, warning, with-help), the list traits (multi-select, count, position, filter), the item traits (value, selected text, checked, expanded, child count, level), the editor traits (read only, multiline, password), and the numeric ones (number, min, max, unit) — about twenty in all, deliberately held there. A program declares its own keys the same way it declares core ones: by putting `[Field]` on a property of an `Element` subclass. The generator (`Srui.Generators`) binds the property to the `Fields` member of the same name when one exists and the type converts, and otherwise declares a `{Name}Field` key on the type, so a spreadsheet cell or a card can carry as many fields as its lines need without touching the core set. A field's value is whatever type the key says — a `Position` is an index and a total, a `Role` is a registry entry, checked is a nullable bool — never prose: what a field sounds like is a reader's decision (section 7.3), which is what makes translation, per-reader ordering, and sound-based readers possible. A field that reads null is absent: a nullable key (`Field<string?>`, `Field<bool?>`, `Field<Position?>`) is one that can be, and null is the only spelling of it — a widget with no name, an item with no checked concept, an unnumbered list's position, a search box's "searching" while nothing is being searched. An absent field is left out of the description, so an arrival never speaks it; a field that goes absent under the user is still a delta, delivered with a null value, so a reader that wants to say "Selection removed" can, and one that does not renders nothing. An empty string is never absence: an empty edit box's value and an empty query are values, with their own words ("blank", "no filter").

Two kinds of `[Field]` property exist. A **partial** one with no accessor bodies is implemented by the generator: a stored value, or — once `Element.Bind` has connected the key to a getter and optional setter — a read through the program's model and a write to it. A bound field never needs synchronizing: a slider whose number is bound to the mixer reads the mixer, and the user's arrow key writes the mixer through the setter. A binding with no setter is a display, and a widget whose input would write it throws. An **ordinary** property with `[Field]` is registered as it is, which is how a computed field is declared (a list's count, a table cell composed from a cursor). Either way the generator emits the type's `DescribeFields` (every non-null field into a `FieldSet`, ancestors first) and its keyed `TryGet`/`TrySet`, and those three are the generator's alone: the analyzer refuses a hand-written override, because everything a description could once decide by hand now has a home that cannot disagree with the properties — presence is the getter, place is the attribute, and a fact the role's word already states is the role's (`Role.Implies`, section 7.3). A declared key can say where it is read: `[Field(After = nameof(Value))]` or `Before`, naming a core field or one of the type's or its bases', travels on the key as its default place, which a reader may override; a core key's place is the reader's alone. Getters are read at the tick end for the focused widget and the item under its cursor, twice per tick at most, so they must be cheap and pure.

Fields have a scope only by where they are read from: the focused widget's own fields are control-scoped, and the fields of the item under its cursor (`Widget.CurrentItem` — a list's selected item, a tree's cursor node, a tab control's active tab) are item-scoped. The same key serves both — a check box's checked state and a list item's checked state are both `Fields.Checked` — and readers may render them alike or apart.

`Role` is a registry, not spoken text: `Role.Button`, `Role.List`, and the rest are identities a reader maps to words, and a widget authored from the base declares its own (`new Role("table")`). Role-less widgets (`Role.None`) announce as their name alone. Which keys a widget consumes during normal interaction — the basis of shortcut conflict detection — is the widget's own declaration (`Widget.ReservesKey`), not a property of the role.

## 4.3. Mutation

Programs build UI by constructing widgets (each widget inserts its node under its container at construction) and change it through widget properties, or leave it to bindings. Mutations are synchronous and immediately visible, and none of them speaks: the engine describes the focused widget at the end of the tick and reads the difference (section 7.2). So there is no distinction between a programmatic change and a user-driven one, no order to get right between moving focus and changing state, and no silent variant of anything — a widget that wants a change of its own kept out of the reading calls `Suppress` for the tick (an edit box whose typing event is the better voice for the line it changed), and one that wants an unchanged field read again calls `Reread` (a slider at its edge saying its number). Hiding is structural: hiding the focused widget, or an ancestor, moves focus to the nearest reachable node, and the tick end reads the landing as the recovery it is. Disabling the focused widget moves nothing: it reads "unavailable" and focus stays, because disabled widgets remain reachable (section 8). Removing a widget removes its subtree, and focus recovers to the nearest surviving focusable node.

## 4.4. Layers

The tree maintains a stack of layers for modal UI. Each layer has its own roots, focus, and default primary/cancel widgets (Enter and Escape targets). Only the top layer is navigable. Pushing a layer opens a dialog or palette; popping it removes the layer's nodes and restores the previous layer's focus. The base layer cannot be popped.

Dialog conventions live in the widget layer, not the engine: there is no dialog role (the prompt is a Label preceding the widgets, announced as context when the dialog opens), Escape closes a dialog automatically when no cancel widget claims it, and the canned dialogs (message, confirm, custom button rows, reviewable read-only status text) are `SruiDialogs` helpers. Canned dialog buttons carry the Windows-conventional Alt+letter activation shortcut, assigned first-free-letter within the dialog and spoken with the button; widget shortcuts only match within the active layer, so these never collide with the window underneath.

The result pattern is deliver first, close second: a handler mutates the ground, announces its outcome, and then calls `Close`, so the closing restore reads the world the result left (section 8's restore rule). A delivery may freely open a dialog of its own before closing — `Close` on a dialog with dialogs still open above it defers: the dialog is condemned, stands (uninteractable, since only the top layer is navigable) until the last dialog above it dies, and then the collapse cascades — every condemned layer pops in one motion, `Closed` firing per dialog as its layer actually goes, and focus lands on the deepest surviving layer with a single restore read — under the `Changes` restore verbosity, a delta against the state the user last heard before the excursion began. `Close(nested: true)` is the forcing form: it takes the dialogs still open above down with it immediately, for teardown rather than delivery. A delivery may also re-home the ground - focus a ground widget, name a new primary or cancel - before closing: focus, primary, and cancel are each a layer's own, and a write naming a node lands in that node's layer, not the active one, so the pop finds the re-homed focus and reads it once, as a recovery, rather than discarding it with the dialog's layer.

# 5. Widget Behavior and Authoring

Widget behavior is virtually dispatched on the widget object itself: when input reaches a focused widget, the engine calls its `OnInput` override, which mutates the widget's own fields and emits action events for what is not state. The built-in widgets (button, checkbox, single- and multi-line edit box with read-only, listbox, filter listbox, tree view, slider, tab control, shortcut field) are ordinary subclasses of the public `Widget` base and double as the reference examples for the three extension paths:

- **Composition** — subscribe to a widget's events (`Changed`, `Activated`, `Toggled`…), or bind its fields to the program's model.
- **Subclassing a built-in** — override its `On*` methods, keeping the base call so composition subscribers still fire (the demo's sound-augmented lists); withholding it is itself the tool when a subclass gates the event, as a press-twice-to-confirm button does. A subclass input handler that reshapes base-owned state just does so — the tick end reads what changed — and owns any editorial announcement; when its announcement says what the reading would say, `Suppress` keeps the field out of that tick.
- **Authoring a new widget kind** — subclass `Widget` directly (a partial class): pass the role to the base constructor, declare the fields readers should know as `[Field]` properties (computed from the widget's cursor, or partial and stored), override `OnInput` to claim input, and emit action events where the change is not state — `AnnounceBoundary` for an edge hit (the item under the cursor is reread with it), `Announce` for a refusal, `Promulgate` for a raw structured event — with `Touch` after moving private state the fields are computed from. Defer program notifications with `Post`/`PostChanged` so handlers never run inside input dispatch. Override `ReservesKey` to declare the combos the widget consumes, and the widget participates in bind-dialog conflict warnings like any built-in. An authored widget is a full citizen of the tab ring, focus recovery, dialog layers, shortcuts, and every attached reader (the demo's table widget is the worked example).

A `CustomWidget` is the degenerate case: focusable, role-less, no behavior — its interaction lives entirely in host bindings over the physical key stream (section 6.4).

Nonstandard keys and actions — anything a user could not predict from the widget's name and role — are documented through `Widget.KeyHelp`, a text property on every widget. Setting it turns on the with-help field ("with help" in the reading) and claims plain F1 while the widget is focused: the framework shows the text in the canned reviewable status dialog, deferred to drain time like any dialog opening. The claim sits between the widget's own `OnInput` (which wins, so a widget kind that uses F1 itself keeps it) and framework navigation; the `Widget.ReservesKey` base implementation reports F1 reserved while help is set, which is why overrides keep the base call. Key help is the sanctioned home for what would otherwise be smuggled into the description and re-spoken on every focus visit (docs/accessibility-guidelines.md, section 8).

Items are elements too. A list or tree holds `Element` subclasses (`ListBox<T>`, `FilterListBox<T>`, `TreeView<T>` where `T : TreeNode<T>`), and an item's fields are what the reader speaks when the cursor lands on it: its `Value` is the line typeahead matches and readers speak, its `Checked` is its own checked state, and an application item adds whatever else its line needs. The non-generic `ListBox` and `FilterListBox` are the forms over `ListItem` — a value and a checked state — and carry the string convenience overloads, which wrap plain strings into items. Because an item is an object, the cursor follows it by identity: through a reorder the selection stays on its item and only its position is news, and when its item goes the cursor lands on the survivor at the same place, which the tick end reads exactly as an arrow move would — or as empty when the last item went. The items are the list's own (`Items`, with `RemoveAt`, `Insert`, `Add`, `SetItem`; the editorial "Deleted X." is the caller's, announced before the call) or the program's (`BindItems` — every read asks the source, so membership follows the model with no call to the list, and the structural operations then throw). A list does not claim Enter — it falls through to the layer's primary widget, the Windows dialog convention; a `ListBox` whose items are themselves the things to open (a file manager, a level select) opts into the Explorer convention with `activateItems: true`, claiming Enter and raising `Activated` for the selected item. A multi-select list (`multiSelect: true`) reads as "multi select list" and lets the user check items independently of the selection — the check is the item's `Checked` field, so landing on a checked item reads "checked" after its line and an unchecked one says nothing (the absence is the signal), and a toggle reads the new state alone. Enter toggles by default — claiming it away from the layer's primary, which is why `multiSelect` cannot combine with `activateItems` in that mode — and `toggleWithSpace: true` moves the toggle to Space instead, freeing Enter (and re-admitting `activateItems`) at the cost of multi-word typeahead, since Space no longer feeds the typeahead buffer. The programmatic surface is `IsChecked`/`SetChecked` (writes the item's field; the tick end reads it when the item is under the cursor) and `CheckedItems` in list order, with `ItemToggled` for user-driven toggles; a subclass refuses a user toggle per item by overriding `CanToggle` — returning false leaves the state and `ItemToggled` unfired, and the framework says nothing, so the override should announce its reason rather than leave a dead key. Filtering (`FilterListBox<T>`) ranks with the list's `Score` — an item against the query, null excludes, higher first; the default is the built-in fuzzy match over `Value`, and a command-palette-style list installs its own to rank recency or pin entries. `Fuzzy` is public for that: the score is a tier for how the query matches — contiguous at the start, contiguous at a word start, contiguous anywhere, then merely in order — plus a small detail within the tier, and a scorer adding a bonus of its own keeps it under `Fuzzy.BonusLimit`, so the bonus reorders among matches of one kind and never lifts a scattered match over a prefix. A keystroke into the filter is not echoed: the cursor returns to the first result and the reading is the result with its position among the matches, reread when it is the same result as before so every keystroke answers; a filter list reads its results as "no results" when none match, and the count, the position (among the whole pool unfiltered, among the matches under a filter — so a keystroke's reading says how much of the pool the query left), and the query ("no filter", "filter ab") are fields of the list.

The tree view (`TreeView<T>`, `T` a self-typed `TreeNode<T>` subclass; the non-generic `TreeView` over plain `TreeNode` is the text-only form) is a list whose items expand, with navigation deliberately branch-local: Up/Down move among the current node's siblings and wrap within them silently — unlike a list's marked wrap, the ring is short and a numbered tree's position report betrays the seam by itself — making a branch a room rather than a region of one long hallway. Right on a branch opens it if closed and steps into its first child, one gesture — landing inside is the expansion report; Left collapses an open branch (the node stays, and its expansion state is what the reading carries: "collapsed") and otherwise jumps to the parent, the "where am I" recovery move; Home/End jump within the siblings; `numbered: true` counts siblings, not the whole tree. A node's fields are its `Value`, `Expanded`, `Checked`, `ChildCount`, and `Level`; readers speak a branch's expansion and count after its line ("Vanilla expanded 2 items") and nothing of the kind for a leaf. Typeahead hunts by structural proximity: the cursor's sibling ring first (outward both ways, wrapping — the room you're standing in), then the rest of the visible tree by tree distance (edges up and down, so a cousin at your level outranks a leaf buried in a neighbor's subtree — never the flattened depth-first index), falling back to collapsed content ranked the same way, which landing reveals by expanding its ancestors. Such a reveal stays provisional until the user engages: the next typeahead landing silently closes whatever the previous one opened that the new match does not sit under — a match typed past was not the goal, so neither was opening its parents — while any other engagement (arrows, Enter, a check, a programmatic move) accepts the expansion as the tree's real state; only branches the reveal itself flipped are tracked, so a user-opened ancestor never closes. A first single letter hunts by that proximity; repeats rotate through the flat visible order instead, so every bearer gets a turn rather than two close matches starving the rest; multi-letter prefixes include the cursor, the list conventions. Enter falls through to the layer's primary unless `activateItems: true` claims it for `Activated`. Nodes carry `Children` (the application's to build) and a widget-stamped `Parent`; the programmatic surface is `Roots`/`SetRoots`/`BindRoots` (the bound form stamps parent links on every read, so structure follows the model), `SelectedNode`, `SelectNode` (reveals and moves the cursor), `Refresh` (re-stamps links after in-place mutation; the cursor keeps its node when it survives, else falls to the first root), and `NodeToggled` for user-driven expansion alone. A multi-select tree (`multiSelect: true`) reads as "multi select tree view" and checks leaves independently of the cursor: Space toggles the selected leaf and no longer feeds typeahead (the `toggleWithSpace` trade), and a branch refuses the toggle with a word — checkability is per node (`TreeNode.Checkable`: leaves by default, branches on opt-in — a checkable branch is an item with properties inside, not a group), so `CheckedNodes` (full tree order, collapse ignored — a check inside a since-collapsed branch still counts) never holds a container. `IsChecked`/`SetChecked` are the programmatic pair and `NodeChecked` reports user toggles.

A tab control's tabs are items too: the active tab is the item under its cursor, so a switch reads the tab and a focus arrival reads the control with it. It owns its panels' visibility once they are attached (`TabControl.AttachPanels`, one panel per tab): the active tab's panel shows, the rest hide and leave navigation, re-synced on every switch — at drain time for user-driven switches (panels are other widgets, so input dispatch never touches them) and synchronously for programmatic `ActiveIndex` changes. Panels are created after the tab control, so they sit below it in tree order.

The edit box is the one built-in whose own action events are the better voice for its changes, and its fields (the current line as `Value`, the selection as `SelectedText`, read-only, multiline, password) reflect that: every editing and movement path suppresses the line and selection fields for the tick and emits typing, cursor, and selection events instead, and only a programmatic `Text` replacement or cursor placement reads through the fields (the new line; a selection that went with a replaced document is not news). The text engine under it deserves note. Text lives in a rope (a balanced tree of string leaves, O(log n) local edits); positions are UTF-16 code units, exposed on the editing surface (`CursorPosition`, `Selection`) with setters that clamp to the text and snap backward onto grapheme cluster boundaries, so a position can never land inside a surrogate pair, a combining sequence, a CRLF, or an emoji ZWJ sequence. Cursor movement is grapheme-aware (text-element segmentation, so combining sequences, surrogate pairs, and CRLF move as single characters), and word navigation uses character-class scans in three flavors: code-editor boundaries for speech context, Windows-style word starts for Ctrl+arrows, and Notepad-style word extents for Ctrl+Shift selection and word deletion. The edit box exposes the engine's geometry as pure position queries — word starts and extents, the word at a position, line bounds and line text, and 0-based line/column ↔ offset conversion (`LineCount`, `LineColumnAt`, `PositionAt`; a column is the code-unit offset from its line start) — all clamping and grapheme-snapping like the position setters, and none of them announcing anything. Movement, by contrast, is announced: the `Move*` family (`MoveLeft` through `MoveToDocEnd`) runs the same handling path as the key each method names, so a programmatic word jump speaks the word Ctrl+Right would, an edge hit reports the boundary, and a collapsing selection behaves like an arrow key. What a move speaks is the unit it lands on: a character for the arrows, Home, and End; a word for Ctrl+arrows; a line for Up, Down, Ctrl+Home, and Ctrl+End — Ctrl+End goes to the very end of the last line and reads that line, and "Top" or "Bottom" prefixes a text-edge move only when the cursor had nowhere to go (Right arrow arriving at the text end is the one landing that says "Bottom"). A password field (`EditBox.Password`) keeps its text and hands it to the program as usual, but everything that reaches the user is masked: the value, typing echo, cursor and word movement, selection, undo, and deletion speak one star per character, no completed word is ever echoed, copy and cut are refused while paste still lands, and the focus reading carries "protected" after the value. Programmatic editing has two entry points, both ignoring read-only (which guards user input, not the program, like the `Text` setter): `InsertText` is the announced form — insert at the cursor, replacing an active selection, spoken like typing the text — and `ReplaceRange` is the silent structural splice under find-and-replace and its kin, whose caller owns the announcement and which maps the cursor and selection endpoints through the edit: positions before the range keep their place, positions after it shift with the length change, positions inside it land at the end of the new text. Editing is undoable (Ctrl+Z, redo on Ctrl+Y or Ctrl+Shift+Z; `EditBox.Undo`/`Redo` are the announced programmatic forms): every mutation flows through one recorded splice point in the editor state, so the history covers user and programmatic edits alike. One undo step is a typing sequence or one bulk operation — paste, cut, a selection delete or replace, a word delete, `InsertText`, `ReplaceRange`. A typing sequence, backspace and delete included, ends only when the cursor is not where the previous edit left it as the next edit arrives, or when ten seconds pass between edits — both checked lazily at the next edit, so no timer runs and wandering off and returning to the same spot continues the sequence. Undoing restores the cursor and selection from before the step — a deleted selection comes back selected — and announces the value at the restored state (the selection or the current line), "Nothing to undo" when the history is empty; redo mirrors it, and any new edit discards the redo steps. Setting `Text` clears the history, because a document load is not an edit; undo never touches the clipboard. Memory is bounded per box by `EditBox.UndoMemory`, a retained-character budget that evicts the oldest steps first and always keeps the newest. Focus entry follows the Windows edit-control convention: a non-empty editor selects its whole text as focus arrives (`SelectAllOnFocus` — on by default for single-line editors, off for multiline ones where a focus visit must not clobber a working selection, assignable either way; off touches nothing) — the focus reading carries the value as selected, and the first keystroke replaces the seed instead of appending to it.

# 6. Input

## 6.1. Vocabulary

A key combo (`KeyCombo`) is a physical key plus ctrl/alt/shift/win modifier state, with a spoken display form ("windows control shift s") and a compact config form ("win+ctrl+shift+s") that round-trips through parsing (`KeyCombo.TryParseConfig`). The Windows key has no semantic mapping of its own: any combo holding it is a `RawKey` for the host's bindings, and it suppresses typing the way Ctrl and Alt do. Its natural home is a system-wide hotkey (section 10), since inside a window the OS claims most of the Win+letter range before any program sees it. The string forms exist for serialization and speech only: every API that accepts a combo (shortcuts, key bindings) takes a `KeyCombo` value, so a malformed combo string surfaces where configuration is parsed, not as a runtime failure at bind time. A logical input (`InputEvent`, an `InputKind` plus payload) is the semantic layer above it: navigation (next/previous, hierarchy moves, mnemonic), widget verbs (activate, move by character/word/line, select, type, delete, clipboard, undo/redo), `SpeakFocus`, `Dismiss`, and `RawKey` for combos with no semantic mapping. The default physical-to-logical map lives in the SDL host and is host-replaceable; the host is responsible for translating platform key events into logical inputs.

The mapping is many-to-one (shift+backspace and ctrl+backspace both mean word-delete), so every logical input from a real keyboard also carries its physical provenance: the combo that actually produced it travels on the event, including for typed characters, whose suppressed keydown is paired with the following text-input event (shift+q is representable even though the typed rune is just "Q"). Shortcut matching and shortcut-field capture read the provenance directly and never reverse-map; a canonical reverse map (`KeyCombo.FromInput`) serves only synthetically injected inputs, which carry none. Widget code matches by the same rule: `InputEvent.Is` answers whether an input was produced by a given combo (or bare key), provenance first with the canonical fallback, so an input handler claims shift+up as shift+up rather than by the logical kind it happens to map to; `InputEvent.IsChar` compares a typed character by full codepoint, so an astral character can never alias a BMP one.

## 6.2. Dispatch

Input events are pushed to the app one at a time (`SruiApp.HandleInput`); there is no frame granularity. Each event is dispatched in a fixed claim order: the focused widget's `OnInput` gets first claim, then framework navigation and layer defaults (tab ring, hierarchy navigation, primary/cancel), then widget shortcuts (section 8), then dialog dismissal, then the host's own bindings (`UnhandledInput`). Whatever handles the event mutates fields or emits action events; queued output is delivered when the tick ends (the event loop ends one after each input; a headless host calls `DispatchEvents`).

Ahead of the whole order sits an optional host gate, `SruiApp.InputFilter`: it sees every logical input first — dialog layers included, so a filter that should stand down behind an open dialog checks `HasOpenDialog` itself — and a true return consumes the input outright. This is the freeze seam for apps that must refuse interaction wholesale (a cutscene, a blocking animation) without disabling or hiding widgets: screens and focus stand exactly where they are. Only the logical stream is filtered; the physical key stream (section 6.4) and the keydown speech interrupt flow regardless.

## 6.3. Time

The engine has no clock; the host feeds one through `SetNow` (monotonic milliseconds) — the event loop does this every iteration, and headless hosts do it themselves. Typeahead timeouts are observed there, and tickers become due there; each due ticker then runs as a tick of its own (section 7.2).

One event-loop iteration is public as `SruiApp.Tick`: advance the engine clock from the app's own stopwatch, advance audio automation, pump and dispatch window input, ending a tick after each input (absent on a headless app, which returns without waiting), end the tick for anything else the iteration did, then run each due ticker as a tick of its own — `Run` is exactly `Tick` in a loop, and `Quit` makes `Tick` return false. A host embedding several apps ticks each of them from its own loop: at most one app owns a window (SDL's event queue is process-global), and the rest run headless, taking input the host forwards through `HandleInput`/`HandleKey`. A tick-driven app runs on real time; deterministic hosts (tests) drive `SetNow`/`DispatchEvents` directly instead, since `Tick` would overwrite an injected clock. Applications read the same clock back through `SruiApp.Now` (the engine clock: frame-coherent, at loop resolution) and `SruiApp.PreciseNow` (a live sub-microsecond reading of the clock behind it; on headless apps it follows the engine clock so injected time stays deterministic). A ticker (`SruiApp.StartTicker`) raises its `Tick` event each time its interval elapses, at `SetNow` resolution, drift-tolerant: a late check fires once rather than bursting to catch up.

## 6.4. The physical key stream

Alongside the logical stream, the host layer reports raw key transitions for game-style input: the initial press, auto-repeats, and the release of every key, the modifiers included — Shift, Ctrl, Alt, and the Windows key each report as one physical key (`Key.Shift`, `Key.Ctrl`, `Key.Alt`, `Key.Win`, left and right folded together), so a bare modifier press is bindable, while producing no logical input of their own. This stream never enters the engine — the engine is semantic, and key bindings are host policy (section 9) — and it is independent of the claim order: a press is reported even when the corresponding logical input is consumed. Because a release can never be consumed and a press can never be hidden, the pairing a game relies on is unconditional. The host also signals the window losing keyboard focus, which orphans held keys: game state that tracks them must be zeroed, as the releases will never arrive.

The widget layer builds per-widget key bindings on this stream: handlers attach to any widget for a combo and phase (press, repeat, release) and fire while that widget is focused (`Widget.BindKey`), with unclaimed transitions falling to an app-level hook (`UnhandledKey`). Press and repeat match the exact combo; release matches the key alone, so a modifier pressed mid-hold cannot orphan the release.

A dialog boundary seals the outgoing layer's input, in both directions: when a dialog opens or closes, every held key gets a synthetic release delivered to the layer being left — its release bindings fire now or never — and the remainder of the current input batch is dropped, so logical inputs aimed at the old layer cannot land in the new one. The real key-up, arriving after the seal with the other layer focused, is discarded rather than dispatched: a release whose hold was sealed away (or forgotten through window focus loss) never fires the revealed layer's release bindings.

# 7. Output Events and Readers

## 7.1. Event streams

The engine produces a single ordered stream of output events, and readers receive it one tick at a time (section 7.2). Accessibility events (`AccessibilityEvent`, public) are of two kinds. **State** is what the tick end reads: `FocusArrived` (focus settled on a different widget than the user last heard — with the cause, `FocusCause`: user navigation, a shortcut jump, programmatic focus, recovery, layer restore, or a re-announcement, so a reader can treat focus the user moved differently from focus that came to the user — and the context entered on the way: the groups, as name and role, plus the preceding labels when a dialog opens), `ItemArrived` (the cursor of the focused widget landed on another item), and `FieldValue` (one field of the widget or of the item under its cursor, with its key, its typed value, and its scope). **Actions** are what widgets emit as they happen: text typed or deleted, a cursor move with what it landed on, a selection change, a clipboard operation, an undo, an editor input with nothing to act on, an edge hit (`BoundaryHit`, with the item under the cursor reread alongside), and the free-form `Announce`. Every event names the widget it concerns; an `Announce` from the app names none. A widget's events reach readers only when that widget is where focus settled at the end of the tick, or a container of it (a composite panel speaks for the children it holds) — a widget the user is not on or in says nothing, which is what lets a confirmation that moves focus to its result be heard as the result alone. A widget that acts on another's behalf can name it (`Widget.SpeaksThrough`) and is then heard wherever that widget would be: a console's input box, run by keys typed while the user reads the output beside it, speaks through the pane holding both, so its echo is heard from the output. The widget focus arrived on in this tick drops its action events — the moves and the typing it did on the way are superseded by its full reading — but keeps its announcements, which are deliberate: a pane that renames a file from a dialog and announces the result is heard as the result, then the restored pane. The app's announcements always speak. Editor events deliberately carry only perceptual content (the grapheme, the echoed word, the spoken context) — never document text; a reader that needs more queries the widget. A read-only editor swallows typing silently — nothing was inserted, so there is nothing to echo — and lets Enter fall through to the layer's primary widget. Program notifications (a button's activation, a widget's `Changed`) ride the same queue as deferred callbacks and are delivered to the widget's own events at drain time — handlers never run inside input dispatch, so they may freely open dialogs or remove widgets. Tick events report elapsed ticker intervals. Programs react to widget events; readers react to accessibility events.

## 7.2. The tick

A tick is one cause's worth of change: one input dispatched, one ticker's handler run, or the program's own mutation between them — drained to quiescence (every callback and activation the cause queued runs, and whatever those queue in turn, in the same tick) and then ended. The event loop ends a tick after each input it dispatches, then one for anything else the iteration did, then one per ticker due at the iteration's clock, in that order; a headless host ends the pending tick with `DispatchEvents`, which then runs the due tickers the same way. Two causes that share a loop iteration therefore read exactly as they would an iteration apart: a key that moves a list's cursor and a timer that then reshapes the pool are heard as the landing, then the reshaping — never as one reading of the settled state, which could cancel to silence and make the key feel dead. The tick end describes the focused widget and the item under its cursor (`Element.Describe`, both field sets) and compares them with what the user last heard: the description taken at the end of the previous tick. If focus settled on a different widget, the reading is a `FocusArrived` and every field, control and item alike. If the widget is the same but the item under its cursor is another object, the reading is an `ItemArrived`, every item field, the cursor's position, and the control fields that changed. Otherwise the reading is the fields that changed, in both scopes. Program code therefore never orders a focus move against a state change, never checks whether a widget is focused before changing it, and never sees an intermediate: five cursor moves in one handler read once, where the cursor ended; a change that reverts within the tick reads as nothing; a focus move followed by a state change reads as the settled state. Two per-tick requests refine the reading: a widget's `Suppress` keeps its named fields (or all of them) out of a delta — never out of an arrival, which always reads in full: a focus arrival, and an item the cursor landed on with the position it landed at, so a list that refreshes with its line changes suppressed (a game whose narration tells them) still reads the survivor when the cursor's item goes — and `Reread`/`RereadItem` put unchanged fields in; a field both suppressed and reread in one tick is read, the reread being the more deliberate request. Both clear at the tick end. The shortcut list is the one field that speaks only with an arrival: a shortcut change is structural.

The list delivered to every reader is ordered: announcements and action events as they were emitted, then the arrival, then the fields. What happened is heard before where the user is, whatever order the handler did things in — a handler that closes a dialog and then announces its result is heard as result first, restored focus second. A layer restore reads by the verbosity's restore mode (`SpeechVerbosity.Restore`, section 8): in full by default, as the fields that changed since the layer was pushed under `Changes` (the push snapshots the widget; an unchanged widget produces nothing), and not at all under `None`. The engine keeps a dirty flag — input, an emitted event, a focus move, a structural change, or a field write on any widget sets it — and a loop iteration where nothing set it skips the description, so an idle application allocates nothing; the explicit `DispatchEvents` always describes, since a host calling it is saying something may have happened, and a field written on an item outside any handler is caught by it. Interruption policy — silencing speech on a keypress, utterance length limits — belongs to the speech reader, not the engine: the app broadcasts `OnInterrupt` to every reader when a key goes down (hosts driving a headless app call `SruiApp.Interrupt` themselves). There is deliberately no urgent announcement variant: every keypress already silences speech, and cutting speech off from a timer or background event is bad screen-reader manners — asynchronous urgency belongs to earcons, not interruption.

## 7.3. Readers

A reader is any consumer of accessibility events: implement `IReader.OnTick` and attach with `SruiApp.AddReader`; every attached reader hears every tick, as one list valid for the duration of the call. The reference reader is the self-voicing `SpeechReader`: it renders each tick with `SpeechRenderer.Default` and forwards the utterances to Prism, and a windowed app installs one automatically. The renderer turns a tick's announcements and action events into one utterance each, in order, and its state into one utterance composed from the fields in the renderer's order — NVDA's name, role, value, states, description, shortcut, with the fields that qualify a role beside it ("multi select list", "edit read only multi line") and an item's own fields around its value ("Vanilla expanded 2 items checked 2 of 5") — each field through a small rendering function of its own. Those functions are a table: the reader's, holding every word the user hears about a field, so "empty", "checked", "1 of 3", "no results", "unavailable" are the renderer's and never the engine's. A program registers renderings for fields of its own (`SpeechRenderer.Register`) and words for roles of its own (`SetRoleName`); an unregistered field speaks its value when that is a string — a composed line — and nothing otherwise. A field's place in the utterance is the reader's order for the core fields, and for a program's field the place its declaration asked for (`[Field(After = ...)]`, carried on the key) unless the reader's registration names another. Two more things are a role's: the fields its word already states (`Role.Implies` — a console's "output" is read only and many lines, so neither is said again on a widget of that role, though both stay present for a braille reader that wants them), and its own wording for a core field (`Register(role, field, render)` — a search box's empty query is "blank" where a filter list's is "no filter"). The `SpeechVerbosity` a reader holds trims the rendering live: widget roles (and with them the fields that qualify a role — multi select, read only, multi line — which are role words), shortcut suffixes, the extras (descriptions and the with-help hint), and what typing echoes (`TypingEcho`: characters, words, both, or nothing - deletions always speak what they removed); name, value, and the actionable states are never trimmed. Anticipated additional readers include braille, a UIA provider (the retained tree and the typed fields map directly onto platform accessibility trees), and logging readers — the test suite's recording reader is one.

# 8. Focus and Navigation

Enter and Escape follow the Windows dialog convention: each layer may designate a primary and a cancel widget, Enter activates the primary and Escape the cancel, and only buttons claim Enter for themselves. A primary or cancel widget that cannot currently act — disabled, hidden, or inside a hidden subtree — does not activate; the input falls through unconsumed. Non-button widgets never claim Enter — there is no per-widget "item activated" event; acting on a list selection is the primary widget's job (it reads the selection) or that of an explicitly bound command. Activation is a `Widget`-level concept: any widget targeted by primary/cancel routing or an activate shortcut raises its `Activated` event.

Navigation has three axes. The tab ring visits every focusable node in depth-first tree order with wraparound; hidden subtrees are skipped, and groups and labels are never focusable. Disabled widgets stay in the ring: in a keyboard-only, screen-reader-first UI, skipping them would make them undiscoverable, so they are read ("unavailable") but inert — input, key bindings, shortcuts, and activation all pass them by. Only hiding removes a widget from navigation. Hierarchy navigation moves along the tree structure itself: to parent, first visible child, or previous/next sibling with wraparound. A group is context, spoken when focus crosses into it: every group enclosing the landing widget but not the widget focus came from is spoken first, outermost in, as "name role" — tabbing into Options hears "Options group Word Wrap check box not checked", the next tab within it hears "Second check box not checked", and nesting reads "Options group Personal group Name edit blank". Landing on the group itself by hierarchy navigation speaks it alone, and stepping down into it then repeats nothing, since the group was where focus came from. A first focus, a recovery, and a re-announcement speak every enclosing group. An unnamed group with the default role is structure, not context, and stays silent; a group given its own role (`new Group(parent, null, new Role("console"))`) speaks that role even unnamed, and a widget's `Role` is its own to set the same way. Widget-internal navigation (arrows inside a list or edit box) is the focused widget's own affair and takes precedence through the claim order.

Any widget may carry shortcuts: key combos with a per-shortcut action — jump to the widget, activate it (its `Activated` event fires, without a focus move), or both, jump first. A widget may carry any number of shortcuts, and the first one added is the one focus readings speak. Shortcuts fire only while their widget is reachable — visible, enabled, outside hidden subtrees — and when several widgets bind the same combo, the first reachable claimant in depth-first tree order wins. Mnemonics (Alt plus a letter) are the conventional jump-action case; the framework treats them as ordinary shortcuts on the Alt+letter combo.

Focus memory remembers the last-focused child of each container so re-entering a container restores position. When the focused node is removed, focus recovers to the nearest surviving focusable node; when a layer is popped, the previous layer's focus is restored. What the restore reads is the verbosity's restore mode (`SpeechVerbosity.Restore`). The default, `Full`, reads the widget as any focus arrival would — the re-orientation every mainstream environment gives, and the one a newcomer can trust. `Changes` reads the delta, not the widget: the user never left it, so its name and role are not news — the fields that changed while the layer was open speak (a rename landing, a listing refreshed under a dialog, a cursor moved), and an unchanged widget restores in silence. `None` says nothing, for the user whose hands already know where they are; a result the dialog announced before closing still speaks in every mode. Only a restore that lands somewhere else (the pushed-from node is gone) always reads in full, attributed as the recovery it is.

# 9. Commands and Key Bindings

Key bindings are host policy. The engine stores no command maps and dispatches no commands: input the claim order leaves unconsumed reaches the app's `UnhandledInput` hook, which matches it against whatever binding scheme the application likes — as do command palettes, categories, jump lists, and persistence.

The toolkit contributes three mechanisms to that host machinery, all public. `KeyCombo.ReservedReason` names the combos the framework itself consumes — plain Tab and Shift+Tab (the focus ring), Alt+letter (mnemonics), Alt+arrows (hierarchy navigation) — each with a spoken refusal for bind dialogs to announce; everything else, including Ctrl+Tab and Escape, is categorically bindable. Bind dialogs query `SruiApp.ReservedReasonFor(combo)` rather than the static property: it adds whatever the app's host reserved (`SruiApp.HostReservations` — under a multi-app host, the app-switching combos; section 10), so the same dialog refuses correctly standalone and hosted. `Widget.ReservesKey` reports which keys a widget consumes during normal interaction, so a bind dialog can warn about combos the focused widget would swallow — custom-authored widgets participate by overriding it. And the shortcut field captures any bindable combo before the framework can interpret it — including Alt+arrows and mnemonics — deliberately releasing only Tab and Escape so the keyboard user can always leave the field.

# 10. Multi-App Hosting

`MultiAppHost` runs several apps in one window: it owns the single `SdlHost`, one shared speech reader over Prism, and one shared sound manager, and multiplexes them across any number of hosted apps. Apps are created through `MultiAppHost.Add(name)` — at startup or at any point while running — which returns a `HostedApp`: a headless `SruiApp` (built into normally) pre-wired to the shared services — the system clipboard, the shared reader, the shared audio (`SruiApp.Audio` on a hosted app resolves to `MultiAppHost.Audio`, one device for the whole program, ticked and disposed by the host), and the host's key reservations. One windowed host per process — SDL's event queue is process-global.

An app leaves through `HostedApp.Close()`: it is removed from the host's list (switching skips it, messages to it drop silently), its `SruiApp` is disposed, and when it was the active app its neighbor is activated with the full switch announcement; closing a background app is silent. Close is idempotent and belongs at drain time, like any operation reaching beyond a widget's own state. A hosted app's own `Quit` is turned into `Close` by the host on the next tick, so an app's exit path behaves identically standalone and hosted. `HostedApp.IsClosed` and its `Closed` event report the transition. `MultiAppHost.AppsChanged` fires on every add and close, and `MultiAppHost.AppsVersion` advances with it — the refresh signal for a launcher or task-list app reading `MultiAppHost.Apps`. A hosted app that subscribes to `AppsChanged` has put a handler into an object that outlives it and must unsubscribe on its own `Closed`; polling `AppsVersion` from its own ticker needs no such care.

An app's own code may throw — a widget handler, a message handler, a ticker — while the host is delivering input, a key, messages, or a tick to it. `MultiAppHost.AppFailed`, when set, receives the `HostedApp` and the exception in place of the exception propagating: the host is then free to close the app, report it, or both, and the loop continues with the other apps untouched. Unset, the exception propagates out of the host as it would from a single `SruiApp`, which is the right default for a one-app program and the wrong one for a shell hosting many. The delivery for the failing app stops at the throw: events still queued in that pass are dropped, which is harmless for an app about to close and recoverable for one kept alive, since the next pass drains what arrives afterwards.

Exactly one app is active at a time; it receives all pumped input through its ordinary claim order, and the host's own `UnhandledInput`/`UnhandledKey` hooks fire when the active app declines. The rest keep running — clocks advance, tickers fire, messages deliver, state mutates — but silently. What a switch says is graded by how the user got there (`SwitchAnnouncement`, a parameter of `Activate`): the switching combos (`NextAppCombo`/`PreviousAppCombo`, default ctrl+tab and ctrl+shift+tab, host-configurable and nullable) name the destination — the app's name followed by its focused widget with context, the window-switch announcement — while a task-list pick passes `FocusOnly`, because the user just chose the name and repeating it is noise, and `Silent` says nothing at all (the caller speaks, or the switch is an invisible restore; the very first focus an app ever establishes still announces itself). `HostedApp.Name` is read at announcement time, so an app renaming itself — an editor adopting its document — speaks correctly from the next switch without ceremony. The switching combos are matched before the active app sees the input, so no app can trap the user, and they are hard-reserved inside every hosted app: `SruiApp.ReservedReasonFor(combo)` — the query bind dialogs use in place of the static `KeyCombo.ReservedReason` — answers with the framework's categorical reservations plus whatever the host claimed through `SruiApp.HostReservations`, evaluated live so a reconfigured switch combo moves the refusal with it. Deactivation runs the app's `FocusLost` (held-key state zeroes, exactly as when the window loses focus) and maintains `SruiApp.IsForeground`, a host-set flag app code branches on — the engine ignores it.

Background speech is policy, applied where the shared reader attaches: a background app's ticks are dropped, except the announcements of apps that set `HostedApp.AnnouncesInBackground` — the flag passes `Announce` events only, never focus or state, because asynchronous urgency from an app the user is not in belongs to announcements it chose to make (or to earcons). Readers attached directly to a hosted `SruiApp` bypass the policy and hear everything, which is the seam for per-app logging.

Apps message each other through the host: `HostedApp.Send(object)` queues into the target's mailbox, and its `MessageReceived` event delivers at drain time — outside input dispatch, on the one thread, whether or not the target is active. A message sent from a delivery handler (including to the sender's own app) waits for the next drain, so self-sends cannot loop a drain forever. Receivers pattern-match on the message type; the toolkit imposes no message vocabulary.

A windowed host also owns the system-wide hotkeys: `MultiAppHost.SystemHotkeys` (`ISystemHotkeys`, null headless) registers a combo with the operating system under a caller-chosen id, so it fires wherever keyboard focus is — the launcher shape — and answers a refusal with the spoken reason (another program holds the combo; the key has no system form). A press arrives as `HostEvent.Hotkey` from the pump and reaches `MultiAppHost.HotkeyPressed` with the id, on the app thread, whether or not the window has focus; the combo itself never arrives as a key, because the OS consumed it. What runs, and whether the window comes forward (`MultiAppHost.RaiseWindow`), is the host program's policy, like every other binding. A registered combo is exclusive across the session — no other program sees it while it is held — so the ranges the OS leaves free (Win+Alt) are where defaults belong, and an in-window binding is never promoted wholesale. On Windows this is `RegisterHotKey` against the SDL window and `WM_HOTKEY` seen through SDL's Windows message hook, which runs inside the pump on the app thread.

The host's loop mirrors the app's: `Run` is `Tick` in a loop (pump and route — ending the active app's tick after each routed input, as a single app's loop does — tick shared audio, deliver messages, tick every app, then run the `Ticked` hook — the host program's own per-iteration work), `Quit` ends it, `TickAt(now)` is the iteration without the pump, at a clock the caller owns — every hosted app runs on the host's one clock (`Now`), stamped on it the moment it is added — and a headless host (`MultiAppHost.Headless`) is driven through `HandleInput`/`HandleKey`/`DispatchEvents`/`TickAt`, which is what `Srui.Testing`'s `TestHost` does. `MultiAppDemo` exercises the whole surface: a Home app whose live task list (rebuilt on `AppsChanged`, activating with `FocusOnly`) fronts three others, combo switching, messaging, the background-announcement flag, and self-closing.

# 11. Native Boundaries

Native code sits behind three hand-written P/Invoke surfaces, each over a DLL staged by `native/build-native.ps1`: SDL3 (window, event queue, clipboard, the Windows message hook), Prism (speech/braille through the running screen reader or platform TTS), and cosmos with phonon beside it (game audio; consumed by `Srui.Audio`). Strings cross these boundaries as UTF-8; native booleans marshal as one byte; there is one callback on the UI path — SDL's Windows message hook, through which the host hears `WM_HOTKEY`; it runs synchronously inside the pump, on the app thread, and only records an id — otherwise the host polls SDL and drains the engine. A fourth, tiny surface over user32 (`RegisterHotKey`/`UnregisterHotKey`) serves the system-wide hotkeys and needs no staged DLL. Struct layouts and constants are transcribed from the vendored native headers, not from documentation.

The toolkit is not thread-safe and does not need to be: one `SruiApp` belongs to one thread. Multiple apps on different threads are fine.

The polling loop is allocation-free at idle. An empty pump or drain returns a shared empty batch rather than a fresh list, a clean engine skips the tick-end description, and readers are called only for a tick that produced something, so an idle application's memory stays flat instead of accruing garbage at the loop cadence. Batches returned by `SdlHost.Pump` are therefore read-only by contract.

# 12. Testing

The toolkit runs fully headless, and the harness for exploiting that ships as its own package, `Srui.Testing`, with no test-framework dependency: assertions throw plain exceptions, so it works under xUnit, NUnit, MSTest, or a bare console.

`Harness` is the abstract core, and `TestApp` is it over a headless `SruiApp`; `TestHost` is it over a headless `MultiAppHost`, whose `Tick` is one host iteration and which a shell's own harness derives from. Either couples the thing under test to a `RecordingReader`, which keeps every tick it hears (`Ticks`, each a copy of its events; `Events` flattens them). Tests build widgets, push input, and assert the utterances a reader hears (`Spoken` ends the tick and renders every recorded tick through `SpeechRenderer.Default` under the live `SpeechVerbosity` of the app or host under test, so a test that trims it hears what a reader would; `Expect` asserts an exact ordered batch; `ExpectNoSpeech` asserts silence — a first-class outcome in a toolkit whose speech rules forbid redundancy). Anything richer than exact batches is ordinary LINQ over the `Spoken` list, or over the recorded ticks themselves; the harness deliberately grows no assertion vocabulary. Every input method, and `Wait`, is a step with the same batch discipline as a scenario line: it discards whatever the previous step spoke, runs, and ends the tick before returning — so deferred work has happened and widget state is assertable the moment it returns, an assertion always describes the last step alone, and speech a test never asks about is out of its scope rather than something it must clear away. `Type(string)` is one step, its echoes one batch. Programmatic mutations open no step, so a test that speaks through them draws the boundary itself with `Drain`; otherwise `Drain` has no role. Input can be pushed at three fidelities: logical inputs directly (`Input`, `Type`), bare RawKey combos (`Raw`), or full key-tap simulation — `Press` delivers the physical Press phase, the logical input, and the physical Release in host order, running the same physical-to-logical mapping the SDL host runs (`InputMapper.MapCombo` is shared, not duplicated) and synthesizing the TypeChar an unmodified printable produces under a US layout; `Down`/`Up` drive the physical stream for game-style input. Combo strings accept the config form and compact modifier initials (`"cas+f4"`; the final segment is always the key). `Wait` advances the injected clock, so typeahead timeouts and tickers elapse instantly and deterministically. `Until(condition, what)` and `UntilHeard(predicate, what)` are the one sanctioned wait on real time — a worker thread landing a result the engine cannot see coming: the clock follows the wall clock, one iteration per poll, everything spoken meanwhile is the next batch, and a timeout fails naming `what` and what was heard. Anything the engine's own clock drives is `Wait`, never `Until`. `Poll.Until` is the same wait for a test that has no harness — a service on its own thread — with an optional action to run before each check.

An exchange can be frozen as a scenario file: a line-oriented plain-text recording, run from a test against the harness's current state (`RunScenario`), which makes a file a composable fragment — shared setup flows replay before further scripted or C# steps. The grammar is closed: a bare line taps a key combo; `down`/`up` hold and release; `type` types the rest of the line; `wait` advances the clock; `say` asserts the next utterance of the current batch exactly; `nospeech` asserts the batch is empty; `//` comments. Each input step drains speech into a fresh batch. A batch nothing asserts is discarded unchecked — scenarios stay silent about speech outside their scope — while a batch anything asserts must be asserted completely. `RecordScenario` re-runs a file's inputs and rewrites its assertion lines from what was actually heard, freezing silent batches as explicit `nospeech`: the approval workflow is record once, read the file, replay forever, and review intentional changes as diffs. Setting the `SRUI_RECORD` environment variable (non-empty, not "0") makes every `RunScenario` re-record its file instead of asserting — one flag re-approves a whole suite after an intentional speech change. Expressiveness requests (partial matching, patterns) are answered by writing that test in C#, never by growing the grammar.

`Srui.Tests` (xUnit) is the behavioral safety net and the harness's first consumer: behavioral tests drive the public surface end to end through `TestApp`. Engine invariants are property-tested with seeded-random generators, including: the tab ring lands only on valid focusable nodes and visits each exactly once per cycle; word-boundary navigation always makes progress and stays in range; the editor's cursor and selection stay within the document under arbitrary operation sequences; the rope agrees with a reference implementation under thousands of random edits. New behavior is expected to arrive with its invariants encoded the same way. `AotDemo --headless` replays an embedded scenario through the published binary, proving toolkit, generator output, and harness compile ahead-of-time.
